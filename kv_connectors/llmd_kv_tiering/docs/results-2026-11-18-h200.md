# GPU results, 2026-11-18: 2x H200

These tests measure pulling a cached prompt from another replica through the tier, against recomputing it. For reference, the same tests also ran on vLLM's in-tree `kvcr` secondary tier (KVCR v0.2.0), on the same nodes, network, vLLM image and router.

## Setup

- GKE, 2 x a3-ultragpu-8g (H200) nodes, one GPU per vLLM pod, Qwen3-8B, 64-token blocks.
- vLLM nightly 0.34.0rc1.dev672, the same image digest for both stacks, unpatched. It runs the Rust frontend on vLLM's gRPC `Inference` API.
- Both stacks use `OffloadingConnector` with `TieringOffloadingSpec` and an 8 GB primary CPU tier. KVCR's stack adds the in-tree `kvcr` secondary tier. This tier adds `LLMDKVTierManager` through `module_path`, with a `kvtierd` sidecar holding a 16 GiB pool.
- The router is the same EPP image for both. It runs `precise-prefix-cache-producer`, then `p2p-source-producer` with `transport: kvcr`, then a random picker. The EPP sends a `kv.fetch` hint with a placeholder hash, and each tier treats every block of the request as fetchable (opportunistic query).
- Transfers run over TCP between pods. Neither stack uses RDMA.

## Results

Each prompt is 11,584 random tokens, with one output token. Each prompt is sent twice. The table reports the second send.

| | This tier | KVCR |
| --- | --- | --- |
| Recompute (first send) | 331 ms | 330 ms |
| Routed to the pod that holds the prefix (GPU-memory hit) | 22 ms (n=13) | 21 ms (n=16) |
| Routed to the other pod, which pulled the prefix | 240 ms median, 282 ms p90 (n=17) | 555 ms median, 567 ms p90 (n=14) |
| Full prefix cached on the second send | 30 of 30 | 30 of 30 |

The two stacks ran one after the other, with no other traffic on the pods.

Breakdown of one pull through the tier (1.7 GB of KV):

- The peer fetch takes 108 to 156 ms. The daemon spreads it over 8 TCP connections and reaches about 90 to 140 Gbit/s.
- Copying from the pool into vLLM's primary CPU tier takes 54 to 131 ms. It gets faster over the first few pulls on a fresh pod.
- vLLM then copies the blocks from its CPU tier to the GPU.

## Longer prompts and a larger model

These are direct requests, with no EPP. Pod A computes the prompt. Pod B then serves the same prompt, either with no hint (recompute) or with a `kv.fetch` hint naming pod A. Each cell is the median of 5 runs. Each stack ran on its own, on the same two nodes. The 32B runs gave both stacks a 20 GB primary CPU tier, and gave this tier's daemon a 32 GiB pool.

| Model | Prompt tokens | Recompute | Pull, this tier | Pull, KVCR |
| --- | --- | --- | --- | --- |
| Qwen3-8B | 11,584 | 0.32 s | 0.28 s | 0.81 s |
| Qwen3-8B | 29,952 | 1.12 s | 0.54 s | 1.39 s |
| Qwen3-32B | 11,584 | 1.40 s | 0.57 s | 1.60 s |
| Qwen3-32B | 29,952 | 4.59 s | 1.03 s | 2.49 s |

Every hinted request had its full prompt cached on pod B, on both stacks. Recompute time grows faster than KV size, with model size and with prompt length. So pulling gains more as either grows. On Qwen3-32B with a 30k-token prompt, the tier's pull is 4.5 times faster than recomputing. KVCR's is 1.8 times faster.

## RDMA

The same direct test on RDMA, with one 400 Gbit/s RDMA NIC per pod (`mrdma.google.com` device claim on GKE A3 Ultra), Qwen3-32B, medians of 5. Both tiers ran on the same two nodes, back to back.

| Prompt tokens | Recompute | Pull, this tier | Pull, KVCR |
| --- | --- | --- | --- |
| 11,584 | 1.38 s | 0.186 s | 0.185 s |
| 29,952 | 4.51 s | 0.425 s | 0.420 s |

On RDMA the tier uses its zero-copy path (`rdma_zero_copy: true`). The source daemon's RDMA helper writes the blocks straight into the destination vLLM's CPU tier, with no pass through the destination's pool. A 29,952-token pull moves 7.85 GB in about 218 ms, about 288 Gbit/s.

Two design choices decided the result. Each was measured on these nodes with a 4 GB NIXL transfer:

| Transfer, 4 KiB-page shared memory | Bandwidth |
| --- | --- |
| RDMA READ, destination pulls | 137 to 162 Gbit/s |
| RDMA WRITE, source pushes | 293 to 307 Gbit/s |

- **Push, not pull.** RDMA READ is limited by how many reads a queue pair can have in flight, so it reached about half of what WRITE did. Huge pages (2 MiB) also brought READ to about 300 Gbit/s, but these nodes do not allow huge pages for shared memory. WRITE needs no node change.
- **No second copy.** The first RDMA version read into the destination's pool and then copied into vLLM. The copy cost 220 to 320 ms for 7.85 GB. Writing straight into vLLM's CPU tier removed it.

How the pull got there, at 29,952 tokens:

| Version | Pull |
| --- | --- |
| RDMA READ into the pool, then a copy into vLLM | 0.92 s |
| RDMA READ straight into vLLM | 0.68 s |
| RDMA WRITE straight into vLLM (current) | 0.43 s |

## What changed to get here

- One TCP connection per fetch made the pull take about 1.0 s. Fetching over 8 connections fixed that.
- Copying on one thread ran at about 9 GB/s. Splitting copies over 8 threads, and mapping the pool with `MAP_POPULATE` so the copies don't page-fault, brought it down.
